## Code Architecture

**Flutter app** (`mobile/`) with a feature-first, clean-architecture-ish folder structure under `lib/`, plus a local design-system package under `packages/`:

```text
mobile/
  lib/
    main.dart                     # Entry point: Firebase (Android-only), DI, category cache warm-up,
                                   # push-notification init, then runApp(ZaytonaApp)
    router.dart                   # go_router route table
    firebase_options.dart         # Generated by flutterfire — Android configured, iOS not yet
    core/
      di/injection_container.dart # get_it service locator (setupLocator / sl<T>())
      di/session_cleanup.dart     # Resets DI-held state on logout
      network/
        dio_client.dart           # Singleton Dio; base URL + JWT auth interceptor
        token_storage.dart        # flutter_secure_storage read/write for JWT
      error/                      # Failure / Result / exceptions used across data→domain boundary
      l10n/locale_controller.dart # Runtime locale switching (ValueNotifier<Locale>)
      notifications/              # FCM foreground/background handling wrapper
      widgets/                    # Small shared non-DS widgets (refresh indicator, spinner)
    l10n/                         # Generated AppLocalizations + app_en.arb / app_ar.arb (flutter gen-l10n)
    features/
      auth/        # login, signup, OTP, logout — data/domain/presentation (bloc/)
      groups/      # groups_home, group_view, create/join/invite — presentation/cubit/groups/
      lists/       # shared shopping lists — presentation/cubit/lists/
      items/       # catalog, add item, list items — presentation/cubit/items/
      histories/   # HISTORY feed — presentation/cubit/
      notifications/
      onboarding/
      settings/
  packages/
    zaytona_design_system/        # Local Dart package (path dependency) — the production DS.
                                   # Presentation-only, token-driven (see docs/ds_conversion_brief.md).
                                   # `mobile/lib/design_system/gallery_page.dart` is a component gallery
                                   # screen that imports it — not the DS itself.
```

**Networking pattern:** every feature's `*RemoteDataSource` holds `final Dio _dio = DioClient.dio`. `DioClient.dio` is a static singleton configured with the base URL (`https://zaytouna-team-1.onrender.com/api/v1`) and a request interceptor that attaches the stored JWT as `Authorization: Bearer <token>`.

**Auth flow:** register/login trigger an OTP dispatch; the OTP verify endpoint returns the JWT, stored via `TokenStorage`.

**State management:** Cubit (`flutter_bloc`) is already the live pattern in every feature's `presentation/cubit/` or `presentation/bloc/` folder — this is not a future target, it's in place. Dependencies (datasources, repositories) are wired through `get_it` (`core/di/injection_container.dart`) and injected into cubits. The design system package stays state-agnostic and never imports Cubit.

**Navigation:** `go_router` (`lib/router.dart`), not `Navigator` push/pop directly in new code.

**Localization:** ARB-based (`lib/l10n/app_en.arb`, `app_ar.arb`) via `flutter_localizations` + generated `AppLocalizations`. Run `flutter gen-l10n` after editing `.arb` files. Locale is switched at runtime through `core/l10n/locale_controller.dart`, not just device locale.

**Push notifications:** Firebase Cloud Messaging is wired for Android only (`main.dart` gates all Firebase init behind `defaultTargetPlatform == TargetPlatform.android` — no iOS `GoogleService-Info.plist` registered yet). Don't assume FCM works on iOS builds.

**Tests:** there is currently no `mobile/test/` directory — the `flutter test` commands above are the convention to follow once tests exist, not a description of current coverage.

## Design System

The production Flutter design system lives at `mobile/packages/zaytona_design_system/` (a local path package, not `mobile/lib/design_system/` — that folder now only holds a gallery screen that consumes the package). It is being converted from the prototype in `design_source/Zaytona_Design_System/` (React + CSS tokens). The full plan is in `docs/ds_conversion_brief.md` — follow its phases in order; do not improvise the system.

Rules:

- **Presentation-only.** The design system imports nothing from domain, data, or feature layers — no Cubit, no models, no repositories, no navigation. Widgets take values in and emit callbacks out.
- **One token source.** All colors, spacing, radii, shadows, and type come from the `ZaytonaTokens` `ThemeExtension`, read via `context`. Never hardcode a hex or px in a widget.
- **Naming.** Widgets are prefixed `Zaytona*`. Every variant is a Dart enum, not a string.
- **Brand invariants are fixed:** 2.5px navy outline; blur-less navy "pop" shadow that presses into itself; pill radii; cream background (never pure white); mint takes navy ink; the 14-point star; mascot avatars; RTL-first.
- **Fidelity source.** The running prototype (`design_source/Zaytona_Design_System/ui_kits/thalaja-app/index.html`) is ground truth for how things look and behave. The manifest and `.d.ts` files are the intended contract — validate them against the prototype, don't trust them blindly.

## Product Vision

Zaytona solves one specific problem: the person who shops for the whole household goes to the store without knowing what everyone needs. The core job is **collection** — aggregating every household member's requests into one actionable list before the buyer leaves.

**Cultural context is load-bearing, not decorative:**

- Target users are Saudi households with a monthly grocery ritual
- One designated buyer shops for everyone, often once a month
- Family members have no reliable way to submit requests before the trip
- The pain is duplicate purchases and forgotten items, not list organization
- Arabic is the primary language — RTL and Arabic-first, not translated

**Zaytona is NOT:**

- A general grocery manager
- A pantry or inventory tracker
- A shopping history tool (history serves the collection loop, not the other way)
- A meal planner
- A budget tracker

Every feature must serve the collection-to-purchase loop. If it doesn't make the buyer's job clearer or give requesters a voice, it does not belong.

## Before You Build

Before implementing any feature, screen, component, or API endpoint — ask. Do not assume. Do not invent requirements.

For **design-system work**, follow the phases in `docs/ds_conversion_brief.md` instead of the story mapping below.

For **product features**, ask these in order, one at a time, stopping when you have enough to proceed:

1. **Which user story does this map to?** State the US-XX ID. If it doesn't map to a documented story, flag it before proceeding.
2. **Who is the actor?** Guest, Member, Admin, or Buyer — and what is their specific goal in this moment?
3. **Does this serve the Saudi household collection problem, or is it generic grocery functionality?** If generic, it needs stronger justification.
4. **What does the correct output look like?** Ask for an example, sketch, or reference before building the wrong thing.

Never start building to show progress. Start building when the requirement is unambiguous.

## Non-Obvious Stack Constraints

- Flutter never calls Supabase directly. No Supabase Auth, no Supabase Realtime SDK, no Supabase Storage from the client. All calls go Flutter → Flask → Supabase.
- Flask-SocketIO is the only real-time channel. Scope: list-level sync only — item added/edited/removed/urgency-tagged. Buying View check/uncheck is NOT broadcast.
- WebSocket broadcast and History record write are the same transaction, not two separate steps.
- JWT is issued and validated exclusively by Flask.
- Supabase Storage is accessed via Flask service key only.

## Known Agent Mistakes

Update this section when a new pattern is identified.

- **Building the generic version.** When a requirement is ambiguous, Claude defaults to how any grocery app would solve it. Zaytona's answer is shaped by the Saudi family context. Ask before assuming.
- **Wrong primary color.** Coral `#FC5E4F` is primary. Night `#0D0050` is text/dark. Frequently swapped.
- **Hardcoding brand values.** Colors, spacing, radii, and type come from the design-system tokens (`ZaytonaTokens`), not literals.
- **Putting state in the design system.** DS widgets are presentation-only: no Cubit, no models, no navigation. State lives in feature layers.
- **Improvising the design system.** Follow `docs/ds_conversion_brief.md` phase by phase. Don't invent components or restyle the brand.
- **Proposing Supabase-native alternatives.** Supabase Auth, Supabase Realtime, and direct client SDK calls are not options.
- **Meta-commentary in deliverable documents.** Artifacts must read as the team's own engineered documents — no reasoning traces, no inline rationale, no "Status: Resolved" commentary.
- **Scope creep during review.** Do not surface out-of-scope features as potential additions when reviewing design or architecture.
- **Re-asking after scope is set.** Clarifying questions belong before generation. Once requirements are established, proceed and state assumptions inline.

## Non-Obvious Business Rules

- Admin role is singular per group. Transfer is atomic — assigning a new admin removes the current admin's role in the same operation.
- `SHOPPING_LIST.group_id` is nullable. Private lists have no group.
- Buying View is fully locked. Add Item FAB is hidden, item edit is disabled — only check/uncheck is active.
- "Possible duplicate" warning on item add is non-blocking. User can proceed regardless.
- Bulk delete requires confirmation. The most recent bulk-delete HISTORY entry exposes a time-limited Undo button — no other entry does.

## Out of Scope

Not in this build: geofencing, occasion/event lists, financial tracking, price tracking, store inventory APIs, custom aisle sorting, in-app chat, AI recommendations, voice input, simultaneous multi-buyer sync.

## Standing rules for this feature

- Ask before assuming. If a requirement is ambiguous, stop and ask me. Do not
  build the generic grocery-app version of anything.
- Surgical changes only. No opportunistic refactors outside the file you were
  asked to touch.
- Debugging protocol: state the symptom, state one hypothesis, add the minimum
  instrumentation to confirm or kill it, only then fix. No fix without evidence.
- No fallbacks. One correct path. Fail loudly on a precondition failure.
- Delete unused code. Never comment it out.
- No file above 180 lines.
- BLoC is the only state layer. Flask is the only backend. Flutter never touches
  Supabase directly.
- use zaytona design system package only
- Arabic and RTL are first-class, not a translation pass.
- Do not implement backend endpoints. Assume the contracts in the backend-needs
  doc and tell me if one is missing.
- LIST_ITEM.item_id is nullable.
  row and does not resolve a typed name to a foreign key. If you find Flutter
  code assuming otherwise, flag it rather than working around it.
